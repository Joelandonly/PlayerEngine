# Ellie systems cooperation audit

This review covers gameplay commands and the shared systems that carry them out in the local Fabric 1.21.1 tree. It uses source inspection and the available Netherbridge, schematic, food, and combat logs. It is not an exhaustive review of the bundled pathfinder or the Player2 service. No behavior changes were made during the audit.

## First change

Wire Netherbridge's verified block and row transitions into the existing shared progress hook. Then make the watchdog track the current phase. A build can gather, travel back, clear, place, and wait for a chunk. Each phase has different evidence of progress. Preserve a hard ceiling for stalled or unloaded work and avoid renewing it for repeated swings, changing targets, or walking in circles.

[SharedTargetRecovery.java](../common/src/main/java/com/player2/playerengine/reliability/SharedTargetRecovery.java) keeps resource mode latched once any child gathers resources. It then applies a 2,400-tick no-output deadline to the root. [SchematicWorld.java](../common/src/main/java/com/player2/playerengine/schematic/SchematicWorld.java) explicitly reports verified output. [NetherBridgeTask.java](../common/src/main/java/com/player2/playerengine/tasks/construction/NetherBridgeTask.java) emitted row telemetry without calling that hook at audit time. The later Netherbridge update calls the hook after verified cells and rows. The latest observed bridge stop was a separate cell timeout. The log reached row 37 at 19,94,88 and showed the no-work counter rising while the target was unset. The saved block was air by the time it was inspected, so the save cannot establish exactly when the fire disappeared.

Regression scenario for the first change. Gather netherrack, rejoin the deck, then clear and build rows without picking up items for more than 2,400 ticks. Verified block changes should keep the goal alive. Repeat with a blocked face and check that it terminates with the active phase, obstruction, and coordinate. Interrupt with survival, then verify that the same row resumes.

## Findings by system

| Priority | System | Current rule and impact | What should drive it |
| --- | --- | --- | --- |
| High | Construction, movement and recovery | Netherbridge uses a 600-tick action ceiling and 32-block restock. The village has a 2,000-tick progress window and a restock threshold that changes at 256 and 1,024 blocks. Schematic placement uses its own 1,200-tick window. A slow approach, interrupted task and unreachable cell receive similar treatment. | Use phase, distance still to travel, reachable working faces, and verified block changes. Report the builder's actual active cell to shared recovery and release only the movement or builder action owned by the current phase. Keep bounded retries for repeated failures. |
| High | Warehouse, inventory and material acquisition | Inventory cleanup already measures live capacity and reserve headroom. Bridge and village restock still request fixed quantities. Schematic prep caps a batch at one stack or 64 and reserves two empty slots at some handoffs even if existing stacks can accept the transfer. | Size each trip from outstanding cells, merge room, reserved ingredients, measured demand, and the cost of returning. Reuse the current inventory snapshot, reservation and warehouse transfer receipts. Preserve a minimum reserve and a high-water mark so Ellie doesn't return to storage after every block. |
| High | Safe Zones, block knowledge and terrain | Shared recovery uses a small block-ID allowlist for incidental clearing. The village water helper also checks literal IDs and names. Netherbridge needed a distinct path for normal and soul fire. | Use block tags, shape, hardness, actual fluid state, replaceability, falling-block risk, block entities and ownership. Share the classification across recovery, farm, bridge and schematic while letting each task specify which actions it authorizes. Safe Zone denial remains absolute. |
| Medium | Warehouse and farm foundations | The shared foundation scanner has a 12-block depth limit. Farm registration also has an 80-farmland cap. Bigger limits alone would make unsuitable sites cost more material or time. | Plan against loaded terrain, reachable support, estimated materials and available work per tick. Allow a larger viable site through incremental planning with explicit bounds. Keep the four-block hydration rule tied to Minecraft mechanics. |
| Medium | Crafting, smelting, food and meat | Crafting-table reach is a fixed 3.5-block check and approach timeout is 300 ticks. Resolver depth is capped at eight. Furnace/smoker have 200/100-tick defaults and narrow fuel retry logic. Food and meat inherit those decisions. | Use the same interaction ray and reach as the actual action. Budget recipe expansion by explored nodes and detect cycles. Use the current recipe cook time and fuel burn duration, then replan when verified stock or accessible fuel changes. |
| Medium | Combat, Patrol, hunting and survival | Patrol's stuck check resets after a block of movement even if Ellie loops. Attack searches fixed 12/24/36-block rings up to 40 blocks with fixed waits. Hero's 32 horizontal and 3 vertical limits are player-selected gameplay behavior. | Track progress toward the route or last sighting, use walkable terrain and recently seen targets to prioritize search, and pause pursuit during emergency defense. Keep the Hero guard envelope and Patrol chase cap as predictable bounds. |
| Medium | WaterFill, setup and exploration | WaterFill has 8,192-volume and 2,048-source limits, a 220-tick placement limit, and a 12-minute job ceiling. Setup lighting has a 12-torch budget. Fixed scan ranges can miss reachable targets near a chunk boundary. | Treat source count and lighting budget as planning limits. Within them, choose placement or search batches by reachable faces, loaded chunks and progress receipts. Let scans grow incrementally within their configured radius. |
| Low | Portal transfer, persistence, progression and observability | Follow transfer already tracks pending work per NPC. Goal receipts are generation-scoped. Progression has explicit balance caps. Observatory reports different kinds of progress under similar messages. | Reuse the existing entity and generation identity for resume. Add phase, active action, last verified change and reason for waiting to diagnostics. Keep progression caps as balance choices. |
| Low | Commands, memory, model integration and indexing | Command syntax is an operator contract. Waypoint, memory, registry enrichment, network payload and model-context ceilings bound memory and IO. | Keep those ceilings. Adapt retrieval and scanning within them by relevance, loaded scope and workload. Treat user-configured limits as settings. |

## Suggested order

1. Wire verified progress into the shared watchdog, starting with the Netherbridge gather-to-build handoff.
2. Give bridge, village and schematic a common restock calculation based on inventory headroom and the current bill.
3. Share terrain classification across construction and recovery, then replace the foundation depth cutoff with bounded incremental planning.
4. Update crafting reach and recipe-based timing. Improve patrol and hunting progress measurements after the shared movement instrumentation is in place.

Use the Netherbridge gap and tunnel, the mob-farm schematic at 111,120,229, and a Patrol interception as the first end-to-end fixtures. Check that movement ownership transfers once, completed work survives interruptions, and protected edits remain rejected.
